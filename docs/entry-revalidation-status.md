## Restoration and testing rules

1. Freeze the candidate sources relevant to a group and identify its exact changes.
2. Run each original whole-case replay and the relevant new negative/positive
   boundary tests. Review full outputs and the entire original clause, including
   affected current guidance. Independently explain expected differences; do not
   generate expected answers by copying actual output.
3. Retain original packets and publish a separate dated current-source review and
   execution receipt. If older captured responses remain relevant, state that
   they are retained observations, not newly generated ones. Add new responses
   only when a changed behavior or coverage gap needs them.
4. Restore only the reviewed cases in the ledger, with an explicit current-evidence
   link and current dependency pins. Keep their historical evidence intact and
   update the explicit current-case assertions in the ledger integrity test.
5. Run the complete current behavior/runtime suite as an independent integration
   gate. This registration change neither deletes nor skips those tests, fixes
   their failures, nor turns an unavailable historical compatibility check into
   current success. Native/device and publication checks remain separate.

New-entry checks should cover missing, withdrawn, stale, conflicting and
comparison-only choices; asset-only statements; selected local execution with VPS
egress; unknown/no resources and direct access; host/guest separation; local
HTTP/mixed entry versus final SOCKS5 exit; sensitive/extra input rejection; and
preservation of exact recovery obligations. A completed questionnaire alone never
opens an action, configuration or network-probe gate.
