## What actually ran

`tests/test_acceptance_history_pause.py` runs six independent regressions against `interview_flow.py`. It includes full handwritten expected question objects for history/device clarification and exact G1/G2/G3 gate expectations. `--replay` retains actual full states, applicable questions, next question and assessments. File, DNS/socket and subprocess calls are denied during these in-memory operations after imports. This is a tested callable boundary, not OS-wide isolation.

The synthetic prior context is supplied explicitly as `COMMON`; it is not inferred from a short user utterance. Synthetic narrative scenarios describe intent only. `prepared-synthetic-exercises.json` separately supplies exact proposed user turns and review criteria for a future guided dialogue exercise. **No model dialogue was run or generated by these tests.** The runtime does not parse those natural-language utterances; a trusted host maps truthful explicit reports to stable IDs and context.

### T31 observed trajectory

1. Current `Q-C04=active` and past `Q-C03=past_suspension` are separately stored as reported account-bound facts, each with source and reporting time. The past event month, `2025-11`, is stored in Q-H02 and never replaces the reporting time or current usability claim.
2. With no selected-device history yet supplied, the first exact question is Q-D01. The current SKILL requires that distinction; a past account restriction does not establish that this selected device was involved. The fixture truthfully answers `other_device_only`.
3. The relevant historical path is exactly Q-H01 through Q-H08, then no further question. It records the affected object, event/recovery, notice availability, preceding action, old device/client, current case status, preservation and relevant changed conditions. This is a controlled one-answer-at-a-time API replay, not a requirement to ask supplied facts twice or to send eight questions together. The host must absorb facts already supplied in one turn.
4. Every intermediate state keeps local explicit choice, current account active, no current incident classification, no VM/VPS or payment branch, PC0, blocked G3 and no persistence consent. No cleanup scope is selected; the final cleanup projection has trigger/next_step `none`, action_authorized false and execution_status not_run.
5. Once all relevant reported facts are present, G1 is complete and G2 planning passes. The history alone has not forced migration, denied the current account or asserted a hardware blacklist. This is planning completeness, not environmental or account verification.
6. Additional route variants retain each existing explicit local/VM/VPS choice after the past history is recorded and after serialization/loading. The account facts do not choose a new deployment route.
7. A negative control supplies a genuinely later `Q-C04=suspended` report. It receives current incident priority and fresh clarification while the prior history and local route remain preserved. Thus the positive historical case does not suppress a real current incident. The existing extra G2 reason is `device_cleanup_incident_triage_required` because a D01 projection is present; the test pins that actual value without claiming that this incident occurred on the historical device.

### T47 observed trajectory

1. The host maps an explicit pause request to `paused=True`. The same operation is exercised in incomplete normal intake, a fully answered planning state and current incident triage.
2. Repeated calls emit no next question. G1 becomes paused, the existing unresolved-field list and all facts remain unchanged, G2 is blocked with conditional_plan_only true and G3 remains blocked. Even the previously complete planning state does not silently stay passed.
3. The runtime's internal applicable-question list remains available for host logic. Active guidance forbids rendering that registry as a form. The host may acknowledge the pause or give a short gap summary; it must not use the internal list to continue the whole questionnaire.
4. No persistence consent follows from pausing. Unauthorized serialization is rejected; separately approved in-memory serialization and loading preserve pause and revoke saved save/export consent. Neither elapsed time nor loading is treated as continuation.
5. `set_context(paused=False)` is rejected. A later explicit `resume_interview` retains facts but introduces a current scoped review before personalized planning can continue. It opens neither G3 nor contact. The T47 condition is stopping on pause; this extra negative boundary does not claim all T16 resume behavior.

## Sentence-level active guidance review

### T31

- **SKILL start instruction 2:** reuse supplied facts and distinguish the selected device's history with Q-D01 when absent. It explicitly prohibits inferring this device's involvement from an account history. This supports the initial device question only when genuinely missing.
- **SKILL selected-device history paragraph:** account history, device history and current account restriction are independent; do not infer a hardware blacklist. The fixture's currently active account and old other-device event are therefore compatible facts rather than a current emergency.
- **Intake core registry Q-C03/Q-C04:** Q-C03 is reported suspension history versus ordinary errors; Q-C04 is registration/current reported login status, without opening Claude in PC0. Keeping both facts separately satisfies the current/history distinction without fabricating a live check.
- **Intake history registry Q-H01–Q-H08:** event date and recovery, exact notice availability, sequence rather than cause, contextual device/client, current case status and preservation have distinct meanings. Reported history need not include unavailable original evidence. The relevant device/network comparison does not authorize a blacklist conclusion.
- **Intake Scheduling route paragraph:** only explicit choice, task context or accepted default selects a route; the unaccepted default is just a proposal. A past incident is not a selection instruction.
- **Incident triage items 1–5:** actual current restriction gets priority, ordinary errors are differentiated, existing projects/evidence are preserved, and factual notes cannot invent cause or certainty. These rules support both the historical positive case and the later-current-incident negative control.
- **Routes M01/common-route rules and stop boundaries:** route choice is independent of proficiency; missing evidence or denied capability pauses dependent work rather than silently switching routes. D-SPEC §5.5 independently states that an incident does not automatically change the chosen route; §6.6–6.7 distinguishes current status and history.

### T47

- **Intake Scheduling opening paragraph:** ask one decision at a time, absorb supplied facts, allow unknown/decline/pause/limited plan, and never display the whole registry as a form. This is the host composition needed when `next_question` is None on pause.
- **Intake G1 sentence:** paused and complete are distinct outcomes. The regression checks that exact distinction even when the pre-pause state was complete.
- **Intake G2 sentence:** unresolved prerequisite facts support only a conditional plan. Stopping questions cannot manufacture enough evidence for an executable plan.
- **Intake G3 sentence and contact policy permissions paragraph:** answers, plan acceptance, host permission, device privilege and concrete action/contact authorization remain separate. The pause request grants none of them.
- **Intake interruption/resume paragraphs:** saving/loading is distinct from an actual continuation event; explicit resume asks one relevant current-change summary and clears saved permissions. The tests verify that loading alone cannot undo the pause.
- **D-SPEC §6.4 and §7.3:** pause is an explicit valid exit at any step and the question library exists for coverage, not endless mandatory questioning. The active guide implements this rule without converting pause to success.
